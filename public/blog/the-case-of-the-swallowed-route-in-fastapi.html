The Case of the Swallowed Route in FastAPI

How Starlette,Django,Werkzeug,Falcon and sanic match URLs under the hood.

March 15, 2026 / 13 min read Read on Substack ↗

Last week while working on a codebase that use FastAPI , I encountered a problem. The endpoint I was pinging threw an error that should never have come from the route I had just written. My first hypothesis was that I had not reloaded the server after the changes, so I restarted it, pinged again, and got the same error. I was surprised. To dig further I dropped a print statement at the very top of the endpoint, before any function call, just to confirm which handler was actually being invoked. What I found was that a completely different endpoint was being called, one I had not touched.

I did a global search through the codebase to see if there was another route registered at the same path and found nothing. But here is how my routes were arranged :

@app.get(”/tests/{test_id}”)
async def get_test(test_id: str):
    return 12

@app.get(”/tests/metrics”)
async def get_metrics():
    return 1

Every request to /tests/metrics was being swallowed by get_test, with metrics being passed in as the test_id. So to temporarily unblock myself ,I changed the metrics route to /tests/metrics/q and it worked, but I was still confused about why. I always assumed the routing logic of such a framework must be doing exact matching or a dictionary lookup, in which case a static path like /tests/metrics should never collide with a dynamic route with a pattern like /tests/{test_id}.

So I opened the router file, looked at the order in which routes were registered, and noticed that get_test was above get_metrics. To test whether order was the cause I moved get_metrics above get_test, restarted the server, and pinged /tests/metrics. This time I got 1, meaning I was hitting the correct endpoint. So I now knew that order matters in Starlette (FastAPI uses this for routing), but the question is why.

How Starlette actually matches routes

I went into the Starlette source code to see how requests are routed. What I found is that it does not do exact matching. It compiles each registered route path into a regex and stores those regexes in the order the routes were registered. When a request comes in, Starlette walks through these regexes one by one and routes the request to the first one that matches.

The function responsible for this is compile_path() in starlette/routing.py (Link to the code file):

# Match parameters in URL paths, eg. '{param}', and '{param:int}'
PARAM_REGEX = re.compile("{([a-zA-Z_][a-zA-Z0-9_]*)(:[a-zA-Z_][a-zA-Z0-9_]*)?}")


def compile_path(
    path: str,
) -> tuple[Pattern[str], str, dict[str, Convertor[Any]]]:
    """
    Given a path string, like: "/{username:str}",
    or a host string, like: "{subdomain}.mydomain.org", return a three-tuple
    of (regex, format, {param_name:convertor}).

    regex:      "/(?P<username>[^/]+)"
    format:     "/{username}"
    convertors: {"username": StringConvertor()}
    """
    is_host = not path.startswith("/")

    path_regex = "^"
    path_format = ""
    duplicated_params: set[str] = set()

    idx = 0
    param_convertors = {}
    for match in PARAM_REGEX.finditer(path):
        param_name, convertor_type = match.groups("str")
        convertor_type = convertor_type.lstrip(":")
        assert convertor_type in CONVERTOR_TYPES, f"Unknown path convertor '{convertor_type}'"
        convertor = CONVERTOR_TYPES[convertor_type]

        path_regex += re.escape(path[idx : match.start()])
        path_regex += f"(?P<{param_name}>{convertor.regex})"

        path_format += path[idx : match.start()]
        path_format += "{%s}" % param_name

        if param_name in param_convertors:
            duplicated_params.add(param_name)

        param_convertors[param_name] = convertor

        idx = match.end()

    if duplicated_params:
        names = ", ".join(sorted(duplicated_params))
        ending = "s" if len(duplicated_params) > 1 else ""
        raise ValueError(f"Duplicated param name{ending} {names} at path {path}")

    if is_host:
        # Align with `Host.matches()` behavior, which ignores port.
        hostname = path[idx:].split(":")[0]
        path_regex += re.escape(hostname) + "$"
    else:
        path_regex += re.escape(path[idx:]) + "$"

    path_format += path[idx:]

    return re.compile(path_regex), path_format, param_convertors

So /tests/{test_id} compiles to the regex ^/tests/(?P<test_id>[^/]+)$, where [^/]+ means “one or more characters that are not a forward slash.” And /tests/metrics compiles to ^/tests/metrics$.

Now here is the thing I had not thought about clearly until I printed both patterns and tested them manually. If you pass the string /tests/metrics through the regex for /tests/{test_id}, it matches, because metrics is a valid sequence of non-slash characters. The static path /tests/metrics is a perfectly valid match for the dynamic pattern.

You can run this yourself to see:

import re
# Regex compiled from /tests/{test_id}
dynamic_pattern = re.compile(r”^/tests/(?P<test_id>[^/]+)$”)
match = dynamic_pattern.match(”/tests/metrics”)

if match:
    print(”dynamic route matches /tests/metrics”)  # this prints
else:
    print(”no match”)

# Regex compiled from /tests/metrics
static_pattern = re.compile(r”^/tests/metrics$”)
match = static_pattern.match(”/tests/test-1234”)

if match:
    print(”static route matches /tests/test-1234”)
else:
    print(”no match”)  # this prints

The dynamic route is broader. It matches anything the static route matches, but not the other way around. So if the dynamic route is registered first, it will always win, and the static route below it will never be reached.

The practical rule that comes out of this is simple : always register static routes before dynamic ones that share the same prefix. If you have /tests/metrics and /tests/{test_id} in the same router, metrics must come first, otherwise the dynamic route swallows it every time. or just make the routes more distinct like /tests/metrics/info to avoid the problem . Given FastAPI's dominance in modern Python backends, keeping this quirk in mind will save you a lot of debugging time if you ever come into such problems like me.

Does Django have the same problem?

After understanding what was happening in Starlette, I installed Django and repeated the same experiment , dynamic route registered above the static one - to see if it would suffer the same fate. It did. Django routed the request to the dynamic endpoint, completely swallowing /tests/metrics/.

To understand exactly why, I went into Django’s source. The URL resolution is handled by URLResolver in django/urls/resolvers.py, which iterates through your urlpatterns list strictly from top to bottom. It stops at the very first pattern that returns a match.

However, looking at the RoutePattern class and the _route_to_regex function, there is an interesting optimization in how Django handles individual routes. The current implementation in RoutePattern.match looks like this:

class RoutePattern(CheckURLMixin):
    regex = LocaleRegexRouteDescriptor()

    def __init__(self, route, name=None, is_endpoint=False):
        self._route = route
        self._regex, self.converters = _route_to_regex(str(route), is_endpoint)
        self._regex_dict = {}
        self._is_endpoint = is_endpoint
        self.name = name

    def match(self, path):
        # Only use regex overhead if there are converters.
        if self.converters:
            if match := self.regex.search(path):
                # RoutePattern doesn't allow non-named groups so args are
                # ignored.
                kwargs = match.groupdict()
                for key, value in kwargs.items():
                    converter = self.converters[key]
                    try:
                        kwargs[key] = converter.to_python(value)
                    except ValueError:
                        return None
                return path[match.end() :], (), kwargs
        # If this is an endpoint, the path should be exactly the same as the
        # route.
        elif self._is_endpoint:
            if self._route == path:
                return "", (), {}
        # If this isn't an endpoint, the path should start with the route.
        elif path.startswith(route := str(self._route)):
            return path.removeprefix(route), (), {}
        return None

    def check(self):
        warnings = [
            *self._check_pattern_startswith_slash(),
            *self._check_pattern_unmatched_angle_brackets(),
        ]
        route = self._route
        if "(?P<" in route or route.startswith("^") or route.endswith("$"):
            warnings.append(
                Warning(
                    "Your URL pattern {} has a route that contains '(?P<', begins "
                    "with a '^', or ends with a '$'. This was likely an oversight "
                    "when migrating to django.urls.path().".format(self.describe()),
                    id="2_0.W001",
                )
            )
        return warnings

There is a clever detail here : for routes with no dynamic segments, Django skips the regex entirely and does a plain string comparison. This is faster and exactly correct meaning /tests/metrics/ will only match /tests/metrics/.

But this is purely a performance optimization for evaluating a single route. It does not reorder your routes or prioritize static ones over dynamic ones. If a dynamic route with a string converter (which matches any non-empty string excluding /) comes first in urlpatterns, it will happily accept “metrics” as a valid variable before the static route ever gets evaluated.

You can run the experiment to verify :

import django
from django.conf import settings
settings.configure(ROOT_URLCONF=__name__)
django.setup()
from django.urls import path
from django.http import HttpResponse
from django.test import RequestFactory

def get_test(request, test_id):
    return HttpResponse(f"dynamic: {test_id}")

def get_metrics(request):

    return HttpResponse("static: metrics")

# Dynamic route registered FIRST, static route second

urlpatterns = [

    path("tests/<str:test_id>/", get_test),

    path("tests/metrics/", get_metrics),

]
factory = RequestFactory()
request = factory.get("/tests/metrics/")
from django.urls import resolve
match = resolve("/tests/metrics/")

print(match.func.__name__)  # prints get_test, swallowing get_metrics

When you run the above codeblock you will see get_test in your terminal. So one must put static routes above dynamic routes when using Django just like FastAPI.

What about Flask?

Flask’s routing works differently from both of the above, and this is where it gets interesting. Flask delegates all URL matching to Werkzeug, specifically to its Map and Rule classes. When you decorate a function with @app.route, Flask adds a Rule to its internal url_map, which is an instance of Werkzeug’s Map.

The key difference is that Werkzeug does not match in pure registration order. It sorts rules by specificity before matching. From Werkzeug’s own source and documentation :

Current sorting implementation:

1. rules without any dynamic arguments come first (static routes win)
2. more complex rules come before simpler ones
3. within equal complexity, earlier registration wins

So if you register a dynamic route before a static one in Flask, Werkzeug still puts the static route earlier in the matching list because it recognises it as more specific. You can see this behavior yourself :

from flask import Flask

app = Flask(__name__)

# Dynamic route registered FIRST
@app.get("/tests/<test_id>")
def get_test(test_id):
    return f"dynamic: {test_id}"

# Static route registered SECOND
@app.get("/tests/metrics")
def get_metrics():
    return "static: metrics"

# Print the sorted url_map to see the actual matching order
with app.app_context():
    for rule in app.url_map.iter_rules():
        print(rule.rule, rule.arguments)

# Using a test client to explicitly show precedence
with app.test_client() as client:
    resp = client.get("/tests/metrics")
    print(f"\nResponse from /tests/metrics: {resp.data.decode('utf-8')}")

Flask protects you from this particular trap automatically. A request to /tests/metrics will always reach get_metrics, regardless of the order in which you define your routes. The tradeoff is that Werkzeug does extra work on startup to sort the rules, and the sorting logic has its own edge cases - particularly around the path converter and rules of equal specificity, where registration order still applies.

What about Falcon and Sanic?

After seeing how Flask handles routes through specificity, I wanted to examine how performance-focused frameworks like Falcon and Sanic handle this shadowing problem.

I ran the exact same experiment : registering a dynamic route, registering a static route below it, and then requesting the static endpoint. Both Falcon and Sanic correctly routed the request to the static endpoint, completely ignoring the registration order.

Under the hood, Sanic and Falcon behave differently from Flask, Django, and FastAPI. They do not use sequential regex matching or simple hash maps. Instead, they compile their routes into optimized routing trees (like a Radix tree or Trie). If you want to dive into their source code to see how these algorithms are built, you can view falcon’s routing/compiled file and sanic’s routing/tree file .

When you define routes in Sanic and Falcon, they construct a tree where static string segments act as explicit branches, and dynamic variables act as fallback nodes. When traversing this tree during a request, explicit static branches are always prioritized over variable nodes.

For example, Falcon’s CompiledRouter goes as far as dynamically generating a Python string of nested if/elif dictionary lookups for the entire routing tree, and then uses Python’s compile() function to evaluate it into a highly-optimized matching function at startup .

Sanic operates somewhat similarly by building a Node structure (a Radix Tree). When finding a route, Sanic navigates down the nodes, looking for exact string matches first before falling back to parameterized children segment.
You can test both of these implementations on your own machine. Here is the code to prove that Falcon correctly routes to the static get_metrics handler despite being registered second.

import asyncio
from sanic import Sanic
from sanic.response import text

app = Sanic("RouterExp")

# Dynamic route registered FIRST
@app.get("/tests/<test_id>")
async def get_test(request, test_id):
    return text(f"dynamic: {test_id}")

# Static route registered SECOND
@app.get("/tests/metrics")
async def get_metrics(request):
    return text("static: metrics")

if __name__ == "__main__":
    # Check routing behavior
    # Sanic resolves routes using a radix tree.
    # We can just simulate a request using its TestClient.
    request, response = app.test_client.get("/tests/metrics")
    
    print("Testing GET /tests/metrics")
    print(f"Response: {response.text}")
import falcon
from falcon import testing

class DynamicResource:
    def on_get(self, req, resp, test_id):
        resp.text = f"dynamic: {test_id}"

class StaticResource:
    def on_get(self, req, resp):
        resp.text = "static: metrics"

app = falcon.App()

# Dynamic route registered FIRST
app.add_route("/tests/{test_id}", DynamicResource())

# Static route registered SECOND
app.add_route("/tests/metrics", StaticResource())

if __name__ == "__main__":
    # Check routing behavior
    client = testing.TestClient(app)
    result = client.simulate_get("/tests/metrics")
    
    print("Testing GET /tests/metrics")
    print(f"Response: {result.text}")

This structural difference explains why FastAPI and Django fail the shadowing test, while the others pass. May be the creators of FastAPI (via Starlette) and Django chose sequential first-match because appending to a list and matching regexes in order is simple, flexible, and starts up instantly. However, as the number of routes grows, sequential regex matching scales at O(N) time complexity. In the worst case, the router checks every previous route before finding the right one.

To observe this, I wrote a benchmark script (with the help of gemini 3.1 pro) to compare the pure routing time complexity of these frameworks. I generated up to 1,000 dynamic routes, appended a single target static route at the very end, and measured the time it took to resolve that static route 10,000 times.

The results highlighted three distinct algorithm complexities :

Linear Time O(N): Django and FastAPI. As the number of registered routes increased by 10x, the time it took to route requests also increased by roughly 10x.

Constant Time O(1): Sanic and Flask. Their routing times remained completely flat regardless of how many routes were registered before the target route. Their specialized internal structures drop requests into the correct handlers almost instantaneously.

Logarithmic Time O(log N): Falcon. It scaled gracefully, sitting comfortably between constant and linear time, reflecting its internal tree traversal overhead.

If O(1) routing is significantly faster and avoids the shadowing trap, why doesn’t every framework build a Radix tree?

The answer might be startup time. I ran a secondary benchmark to measure how long each framework takes to initialize an application and compile its routes.

Django was near-instantaneous. Because it just stores URL patterns in a Python list, it avoids heavy upfront computation. Flask, Falcon, and Sanic, however, took noticeably longer to start up. They have to pay a CPU processing time upfront to parse paths, validate dynamic types, and weave all the routes into a sophisticated tree . FastAPI does not build a routing tree, but it also exhibited a surprisingly slow startup time. Its delay comes from compiling all its route paths into regular expressions upfront, along with the heavy time of parsing Pydantic annotations and generating OpenAPI schemas for all endpoints during initialization.
