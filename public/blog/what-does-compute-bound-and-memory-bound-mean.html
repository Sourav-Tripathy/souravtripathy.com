What does Compute Bound and Memory Bound mean ?

A simple basic analysis from first principles

August 5, 2026 / 6 min read Read on Substack ↗

Anytime you read any blog that describes inference of large language models, you must have come across two jargon terms :compute bound and memory bound. And they brush over it to algorithms or implementations. Let’s break down these two terms from first principles so that any GPU you come across, you can categorise whatever you will be running on it to be its type and work on it.

To understand them we have to start from scratch with what is available with us, when we are working on Inference. We have GPUs and their specifications. Out of those specifications there are three specifications that is important to us. Below is an image of the specifications from NVIDIA’s website.

The three specifications are GPU Memory, GPU Memory Bandwidth and Tensor core FLOPS(floating point operations per second) in different precision’s (we have to select the precision we are working with).

The above image is specification of a H100 GPU from NVIDIA’s Hopper series .

From above GPU memory is 80 GB, Memory bandwidth is 3.35TB/s and if we take FP16 precision(with sparsity) then tensor core flops is 1,979 TeraFLOPs.

Now for compute bound and memory bound understanding, memory bandwidth and Tensor core flops are important.

There is a concept called Machine Balance which is defined as the ratio of peak tensor core FLOPS of a GPU (in selected precision) to that of memory bandwidth. Mathematically

Here if we take H100 SXM in FP16 tensor core precision then machine balance becomes :

The significance of machine balance is that it tells you how many floating point operations your GPU must do to be 100 percent utilised while moving 1 byte from HBM to the SRAM i.e. this is the compute capacity of your GPU theoretically.

There is another concept called Arithmetic Intensity . Arithmetic Intensity is calculated for the arithmetic operation that you will be doing on your GPU. It is defined as the ratio of total number of floating point operations you do to that of total number of memory in bytes you moved for that particular arithmetic operation.

Let’s take an example of a matrix vector multiplication ( y = Ax ) into consideration. The matrix A be N x N and vector x be N x 1, using 16-bit floating-point precision (where 1 element = 2 bytes ).

To perform y = Ax requires N^2 multiplications and N(N-1) additions. So the number of floating point operations is roughly 2N^2 (we are approximating).
Now we have to read matrix A (N^2 elements), read vector x (N elements) and write vector y (N elements). so bytes read/written is roughly 2(N^2 + 2N).

then that makes Arithmetic Intensity (I) :

So, for a standard matrix-vector multiplication (one of the core operations in the decode phase of LLM Inference) we perform nearly 1 FLOPs per byte of memory read.

Earlier we calculated that the machine balance of H100 SXM is about 591 FLOPs/byte but here for a standard matrix vector multiplication we only do 1 FLOPs/byte, which is less than 591 and hence this operation is memory bound because we are not short on compute capacity rather we are bottlenecked by the number of read/write we are performing.

So speaking in terms of generalisation if Arithmetic intensity of an operation is less than Machine balance of the GPU then that operation is memory bound and if the other way then it is compute bound because we need extra compute for our operations.

Taking all these into consideration a standard relationship between Arithmetic Intensity and performance(FLOPs/sec) can be drawn and it will look like :

The above image is called a Roofline Model. It is a simplified visual model of performance used to quickly determine whether a program is bound by memory bandwidth(memory bound) or arithmetic bandwidth (compute bound).

A specific kernel’s x-coordinate tells you instantly whether it is fundamentally compute-bound (points beneath the flat roof) or memory-bound (points beneath the slanted roof).

The point on the boundary, i.e. where the diagonal and horizontal roof meet, is called the “ridge point”. Its x-coordinate is the minimum arithmetic intensity required to be able to escape the memory bottleneck . Computer systems whose ridge point is further to the left are easier to achieve maximum performance on, but the relatively poor scaling of memory relative to compute generally has pushed the ridge points of systems to the right over time.

For an H100 SXM running FP16/BF16 (with sparsity), the compute ceiling hits 1,979 Tensor core TeraFLOPS. Dividing this by its 3.35 TB/s memory bandwidth gives a Ridge Point (Machine Balance) of ~591 FLOPs/Byte .

Now that we are clear on how do we know if something is memory bound or compute bound lets go over its practical implications in a short manner.

LLM inference has two phases namely, the pre-fill phase and the decode phase. In the pre-fill phase, we process all tokens at once meaning we do matrix-matrix multiplications whose arithmetic intensity is pretty high compared to matrix-vector multiplication which we do in the decode phase.

to compare let’s take two square matrices of N x N . The result matrix will also be a square matrix of dimension N x N . For each element we are doing one multiplication and then addition, so that makes nearly 2N operations and then since N^2 number of elements, it becomes 2N^3 FLOPs. and if we take memory read/writes in FP16, 2N^2 for each and sum to 6N^2 making the arithmetic intensity about N/3 i.e. if N/3 is greater than 591 then we are compute bound .

Because of the decode phase being memory bound, algorithms like FlashAttention and techniques like increasing batch size, PagedAttention or KV cache compression, Quantization exist to move it from memory bound towards compute bound.

Next time whenever you are planning to write a kernel for operations in any GPU, you can immediately calculate the operation’s Arithmetic intensity and Machine Balance of the GPU and decide whether it is compute bound or memory bound and proceed for optimisation.

In a nutshell If you are Memory-Bound, don’t waste time trying to optimise the math equations. Instead, focus on minimising memory traffic i.e. use techniques like Quantization (smaller data types), larger Batch Sizes, or Kernel Fusion (combining operations into a single kernel so intermediate data stays in fast SRAM instead of round-tripping to HBM). And If you are Compute-Bound, focus heavily on the math execution i.e. use lower precision (like FP8 or INT8) to unlock higher Tensor Core FLOPS, leverage hardware Sparsity, or parallelize compute across multiple GPU cores.
